# 客户需求、行业标准与独立交付验收

日期：2026-11-08

摘要：客户交付采用独立验收子代理与实际文件检查器共同判定。先冻结客户原始要求和图种，再分别选择各行业标准及检查方法；生成成功、单元测试、文件数量和版本发布不能代替交付验收。本文件提供执行路径，具体字段以检查器实际模板和工具schema为准。

## 默认验收员

完整仓库包含 [luomu-cad-reviewer角色](../agents/luomu-cad-reviewer.md)。正常安装验证入口同时调用安装器，为所选项目配置 Codex/Claude Code 原生角色。首次在客户项目工作时检查其安装状态；缺失则在用户已授权的项目内运行安装入口，保护已有同名代理，不修改模型、Provider或权限。宿主实际发现与角色文件存在分开验证，详见[安装与调用](reviewer-installation.md)。

每次向客户宣称图纸可交付前，主代理默认委派该角色到独立上下文。只交接客户原始任务、源图、最终文件、地区/专业/阶段及已核依据，不交接生成者的通过结论或预期答案。验收员不绘图、不修改客户原件、不替客户删减要求；发现失败交回主代理修复，再独立检查受影响项与跨图关系。当前宿主没有真实独立委派能力时不能伪装成生成者自审。

角色配置、案例评测及校验器属于可复用代理能力建设，不代表训练了基础模型权重。身份字段是流程记录，不是无法伪造的身份认证；仍需保存真实独立会话及执行证据。

默认执行入口为 `workbench_review_agent`：先以 `prepare` 从原合同建立只含原件的 packet，再以明确授权的 Codex home `start` 固定后台 worker，使用同一 operation_id `status` 查询。准确字段以当前 schema 和[作业接口](review-agent-jobs.md)为准。断线或查询超时不另开重复模型；失败后修复问题再显式新建一次审查。个人账户不由安装器猜测或自动选择。

独立进程只暴露本单白名单文件 ID 的只读证据服务，实际文件读取及图像查看都记入本次执行记录。缺少真实模型事件、原始任务读取或必检图像覆盖，不能产出可用的完成回执。即使 `ready` 且模型给出通过，仍须将原报告绑定回原合同，运行最终文件检查；后台接口始终不自行宣布客户交付通过。

## 开工先锁定客户要求

保存原始任务书及原图哈希，逐项建立稳定需求编号，并保留客户要求的图名、专业、格式、可编辑性、纸张、比例、版本、尺寸/尺度来源及修改边界。不得先按生成器能力减少客户清单。

结构化任务书的 `requirements` 和 `required_sheets` 为独立依据；交付契约必须完整对应，检查器禁止删需求、改范围或放宽源期望值。普通文字、PDF、图片先形成绑定原件的需求清单，并由独立验收员核对提取完整性；不能把生成者自行整理的清单视为已经证明没有漏项。

家装19类需求应按本单逐张列出：原始框架、平面布置、家具尺寸、地面铺装、天花布置、灯具定位、吊顶尺寸、开关路线、插座布置、水路布置、立面索引，以及客餐厅、主卧、古筝、次卧、书房、厨房、主卫、公卫立面。示例房间图册或一张柜体立面不能代替整套要求。客户明确无需的图种要保留其原始依据，不能由代理自行删除。

## 分行业选标，分别验收

调用 `workbench_industry(operation="catalogue")` 或 `route`，只展开所选行业及本次图种。[行业分类](industry-delivery.json)为各行业保存独立图种、检查内容、专业复核及标准白名单；[来源记录](industry-sources.json)区分元数据、全文及项目条文证据。

每项 `standard_assignments` 指定 `industry_id`、`standard_id`、采用范围与实际依据。通用标准也必须明确授权给该行业；建筑线宽、建筑尺寸和室内表达不能自动移植到机械、电子、服装等专业。联合项目分别建立行业清单，再检查接口，不合并成无专业区别的一份检查。未知行业或标准范围不明时先补来源与适配，不能套用近似行业。

标准编号和题录只证明检索线索。`reference_redraw` 是忠实参考复绘，不宣称规范设计；`drawing_delivery` 需本项目采用条文及实际复核证据；`engineering_delivery` 还需要对应专业的计算、审核及授权。不得为了通过检查而把客户要求的工程交付降为参考复绘。程序不签发工程资质或认证。

## 实际交付检查

```text
python scripts/verify_delivery.py template --industry interior --report <新契约模板.json>
python scripts/verify_delivery.py review --contract <本单契约.json> --base <获授权的审查目录> --report <新检查报告.json>
```

也可使用 `workbench_delivery(operation="template"/"review")`；`review` 输入契约和授权范围内的 `base`。模板和空字段不能通过。每项客户需求必须关联具体文件和实际检查方法；最终文件、任务书、标准证据和独立报告全部绑定本轮哈希。文件修改后原审核失效。

DXF检查重新打开实际文件，核对单位、原生实体、尺寸定义及显示文字、轮廓/距离/方向/面积等实际测量和图层样式。PDF重新读取每页纸张、页数、物理线重并实际渲染，空白或错误纸张不能通过；图面可读性、内容完整性仍由独立验收员实际查看。STEP/IFC需要相应真实内核和明确检查证据，不能靠扩展名或一份声称成功的报告放行。DWG只走CAD MCP原生重开/回读和预览，不用客户端COM或桌面自动化绕过。缺少支持的必检方法须补能力或取得可核实证据，不能当作通过。

独立报告包含不同于生成者的审核标识、原始任务哈希、每个最终文件哈希、逐需求发现、页码/构件定位、实际预览证据及未解决项。只写 `pass`、使用过期文件或复用生成者身份不能放行。哈希和流程检查也不能单独证明人工观察或专业判断一定正确。

## 放行与交接

只有客户全部必做项、适用专业要求、实际文件检查和独立审查均满足，才能采用最终 `accepted_for_delivery=true`。其他构建工具中的 `ok` 只代表对应操作；MCP构建结果默认携带独立交付审查要求。失败时保留具体需求编号、文件/构件定位及修复要求，修复后从最新成果复验，不回放旧脚本覆盖已确认内容。

对外报告精确写明本次客户任务、文件、实际执行的检查和最终判定。没有完整真实样本的行业不能写成已达到稳定接单能力。不可替代的源尺寸、原始文件、专业审核或宿主权限缺失时明确阻断原因，继续完成其他可执行部分，不制造验收通过记录。
